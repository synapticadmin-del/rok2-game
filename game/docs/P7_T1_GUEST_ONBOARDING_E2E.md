# P7-T1 — تكامل E2E لتسجيل الدخول وتأسيس المدينة (Guest Onboarding)

> **البند (من PLAN.md):** توصيل هوية P6 في التشغيل: ربط أصوات الضغط/الفتح/الإغلاق/الخطأ وهمس الحضارة عبر `URok2ArtAssets`، واستهلاك `URok2WorldIconography` في راسم العالم، وربط `seasonStory` و`URok2SeasonStoryWidget` مع API/HUD ونقطة الدخول.
>
> **هذا الملف:** إثبات أن سلسلة "تسجيل الدخول → قياس الهوية → تأسيس المدينة → القادة → لقطة العالم" تعمل من أول طلب حتى أول لقطة سلطة، على خادم D1/Durable Objects محلي نظيف — وهو بالضبط ما يمثله عميل UE5 في `Rok2BootWidget` (زر الدخول) → `URok2Api::LoginAsGuest` → `URok2Api::InitCity` → `URok2Api::FetchCommanders` → world snapshot. **⚠ معيار القبول النهائي لم يتغير: دورة PIE على UE 5.4.4 توثق في `client-unreal/Docs/PIE_TWO_CLIENTS_ANDROID_ACCEPTANCE.md`، ولا يوجد UE أو Android SDK في بيئة التنفيذ.**

---

## 1. الفلو المختبر (من منظور العميل)

| # | الخطوة | endpoint | ما يثبت |
|---|--------|----------|----------|
| 0 | صحة الخادم + عزل غير الضيوف | `GET /v1/health` ثم `GET /v1/world/snapshot` بلا رمز | الخادم حي، ولقطة العالم تُرفض (401/403) قبل المصادقة |
| 1 | تسجيل ضيف | `POST /v1/auth/guest` بجهاز جديد | حساب جديد + رمز JWT موقع عبر `AUTH_SECRET`؛ اللاعب `null` قبل تأسيس المدينة (FTUE gating) |
| 2 | قياس الهوية قبل FTUE | `GET /v1/me` | الحساب ظاهر واللاعب `null` — مسار `Rok2BootWidget` قبل اختيار الحضارة |
| 3 | تأسيس المدينة | `POST /v1/city/init` (حضارة + اسم) | لاعب جديد برمز محدّث، حضارة واسم محفوظان، قائد بداية من الروستر (`cmd_egypt_starter` Cleopatra)، تعيين مملكة سلطوي (matchmaking `least_fill`)، إحداثيات spawn موثقة، `ON CONFLICT` ضد إنشاء مكرر |
| 4 | قياس الهوية بعد FTUE | `GET /v1/me` | اللاعب الجديد ظاهر بهويته وحضارته |
| 5 | القادة | `GET /v1/commanders` | المملوكون (بما فيهم قائد البداية) + الروستر المركزي (18 قائدًا من `data/commanders.json`) + ثوابت القادة — يمثل `FetchCommanders` بعد كل من الدخول والتأسيس |
| 6 | لقطة العالم | `GET /v1/world/snapshot` | الحالة الكاملة (seasonDay/cities/throne/passes/marches) والمدينة الجديدة ظاهرة — تمهيد لـ `seasonStory` وواجهة القصة |
| 7 | العودة اللاحقة | `POST /v1/auth/guest` بالجهاز نفسه | إعادة المصادقة لنفس الحساب واللاعب بعد FTUE (استمرارية الجلسة) |

الفلو يغطي INT-03 جزئيًا: لقطة العالم أصبحت متاحة فور التأسيس وتحتوي `seasonDay`، وهو ما تستهلكه `URok2SeasonStoryWidget` لاحقًا في تشغيل اللعبة الحقيقي.

## 2. التشغيل الآلي

```bash
# وضع معزول كامل (الأفضل): ينشئ قاعدة D1 وDO جديدة، يطبق الهجرات، يشغّل dev، ويتحقق ثم ينظف
cd game/backend
ADMIN_KEY=<قيمة من البيئة> node scripts/e2e_p7_t1_guest_onboarding.mjs

# وضع مباشر (يتطلب wrangler dev شغالًا):
# 1. تأكد من وجود `.dev.vars` بـ AUTH_SECRET/ADMIN_KEY وأعد تشغيل `wrangler dev` (wrangler يقرأ الملف عند الإقلاع فقط)
# 2. طبّق الهجرات على قاعدة الحالة الافتراضية: npx wrangler d1 migrations apply rok2-db --local
# 3. في طرفية أخرى:
E2E_LIVE=1 BASE_URL=http://127.0.0.1:8792 ADMIN_KEY=<قيمة> node scripts/e2e_p7_t1_guest_onboarding.mjs
```

ملاحظات بيئية مؤكدة خلال التنفيذ (2026-08-13): قاعدة D1 المحلية الافتراضية فارغة قبل أول تطبيق هجرات؛ بدون `AUTH_SECRET` صالح (>24 حرفًا عشوائيًا وغير مسرّب) يرفض الخادم توقيع الرموز برسالة تحذير صريحة؛ `city/init` يُرجع رمزًا جديدًا يجب تحديث `Authorization` بعده.

## 3. دليل قبول PIE المرتبط (لا يستبدله هذا الفحص)

معايير قبول العميل في `client-unreal/Docs/PIE_TWO_CLIENTS_ANDROID_ACCEPTANCE.md` تظل المرجع النهائي لاختبار الضيفين على UE 5.4.4: عميلان مستقلان، جلسة ضيف، تأسيس مدينتين، رؤية مشتركة للعالم، وتحالف/مسيرات. هذا الفحص يثبت الجانب الخدمي من المعيار 1 (تسجيل ضيف + تأسيس مدينة + رؤية مشتركة) دون الحاجة للمحرر، ويبقي معايير الشاشة والـ HUD ودورة الانقطاع/العودة على ذمة دورة PIE.

## 4. ما لا يغطيه هذا الاختبار

صوت `URok2ArtAssets` وهمس الحضارة و`URok2WorldIconography` في الراسم — تغطيها `test:p7-t1-integration` بنيةً، ويثبت تشغيلها الحقيقي PIE فقط. لا يتغير أي كود توازن أو سلوك إنتاجي؛ الفحص قراءة + تشغيل عادي للـ endpoints القائمة.
